# Operating policies for all agents

These rules apply to every current and successor agent across every project, request, and session. They moved here from the root AGENTS.md, which keeps the load list, the instruction-loading rules, and pointers; the text is unchanged. Read this file together with all-agents.instructions.md and the other policies that the root AGENTS.md lists.

## Complete preference application across all surfaces

- Apply the complete current applicable preference set from this repository across every project, folder, workspace, space, repository, conversation, session, task, and equivalent container, regardless of platform terminology. This standing preference applies to all current and successor agents, not only work inside this configuration repository or the container where it was requested.
- Preserve all applicable stored preferences, including concise results-first writing; user-local message and request timestamps; HTML completion and blocked-status email; same-context approved identical sender and recipient; connector-first routing and SMTP fallback; report content and submission evidence; SSH-fingerprint and own-agent quota/reset/forecast footers; supported private usage tracking; durable shared memory; sensitive-data exclusions; private backup overrides; request-time refresh; host-selective setup; authorized assigned-work checks; Git transport, freshness, concurrency, executable-mode, validation, and single-commit safeguards. This inventory is a coverage check, not a replacement for the detailed policies. Preserve future preferences too.
- Apply shared behavior across agents without copying another agent's credentials, quota commands, private state, or product-specific mechanisms. Use the answering adapter's supported implementation. Preserve unrelated instructions, explicit scoped exceptions, private-backup precedence, higher-priority platform instructions, and mandatory permissions.
- Before each final response, check every applicable obligation and distinguish performed, not applicable, pending approval, blocked, failed, and unverified actions. State material omissions and their specific blockers. Do not silently drop a preference because the surface lacks a capability, and do not treat a missing supported quota interface or local SSH access as a reason to omit an otherwise available report.
- For completion and blocked-status reports, follow REPORTING.md on every task. Standing consent establishes reporting intent but does not bypass mandatory platform confirmation. Resolve the actual approved private reporting identity and route; do not substitute a discovered account default. When exact-message approval is required, prepare the full HTML report and present the resolved target and complete draft through the confirmation gate. An unsent report must be explicitly marked pending or blocked; never claim submission or delivery without evidence.
- When configuring a surface, make its supported global bootstrap load this complete set. If only per-container instructions are supported, configure the authorized reachable containers and identify remaining ones. Verify repeated requests and a new session where supported. Repository edits alone do not change account-wide settings, install hooks, update every existing container, or prove universal loading or synchronization. Report policy persistence separately from actual per-surface configuration and observed compliance.

## All-agent message and request timestamps

- Every current and successor agent must prefix every assistant-authored user-facing message with a timestamp in the user's local timezone. This includes all chat surfaces, Projects, CLI and IDE sessions, progress/commentary updates, final answers, approval questions where editable, and completion or blocked-status reports. It is not limited to CLI or VS Code. This shared rule supersedes narrower or host-timezone-based wording in agent entry instructions.
- Use `[YYYY-MM-DD HH:MM:SS TZ (UTC+/-HH:MM)]` when that precision and timezone offset are available. Obtain the actual response time immediately before composing or sending the message. Resolve the user's timezone from explicit context or private runtime configuration; account for daylight-saving transitions. Do not substitute the server's or runner's timezone merely because it is the machine default. Keep any user-specific timezone/location setting private rather than hard-coding it in tracked policy.
- Timestamp each user request as well. Capture the supplied transport/query timestamp when available, preserve its actual precision, convert it to the user's timezone when necessary, and label it as request time. Include it in the first acknowledgment or response for that request and alongside the original request in completion/status reports. Agents cannot rewrite original user chat messages; annotating requests in their own responses and reports does not claim to alter the platform transcript.
- Request, receipt, response, operation, completion, commit, and email-submission times are distinct. Do not reuse request time as response time or describe a commit timestamp as the time of an uncaptured operation. If only local receipt time is observable, label it receipt time and state that the original request timestamp is unavailable. If only minute precision is supplied, do not invent seconds.
- If a reliable current clock or the user's timezone is unavailable, retain the timestamp field and explicitly label what is unavailable. A supplied request timestamp may be shown as request time, never passed off as a freshly sampled response time. Never invent timestamps, timezone offsets, operation durations, or historical step times.
- Begin report bodies, including HTML reports, with the actual preparation/response timestamp and timezone when available. Include the request time, individually captured material-step times, and completion time. Mark unavailable times explicitly; timestamps embedded in the original request or source artifacts must retain their original meaning. Preserve identical approved sender/recipient identities, mandatory send approvals, privacy rules, and the existing report checklist.
- Apply this policy to successor agents and synchronize affected instructions when necessary. Platform-generated messages or uneditable approval/tool UI are outside an agent's formatting control; do not falsely claim those were changed. Persist generic timestamp behavior and non-sensitive preferences, not private request transcripts or identifying location/timezone metadata.

## Shared agent memory and sensitive-data exclusion

- Every agent must save durable, useful, non-sensitive user memory in memory/MEMORY.md in this canonical repository. Include confirmed preferences, decisions, reusable lessons, and project context only when safe to publish. Do not copy raw transcripts, hidden reasoning, private runtime state, or another agent's inaccessible memory.
- Whenever the user asks for something, retrieve the current memory/MEMORY.md alongside the root and applicable agent instructions at task start, and refresh applicable memory before final reporting. Read additional memory files explicitly indexed there when relevant. Do not claim retrieval from memory alone; report unavailable access, missing files, or stale revisions.
- Sensitive data must never be saved anywhere in the repository. This includes personal names, postal addresses, internet addresses such as email addresses, IP addresses, hostnames and endpoints, login names, account identifiers, passwords, authentication tokens, credentials, cryptographic keys, and other authentication material. Existing explicit exclusions remain in force.
- Apply the exclusion to memory, instructions, examples, fixtures, reports, filenames, commit messages, and all other proposed repository content. Never commit a sensitive value even temporarily: deleting it later does not remove it from Git history. Use generic non-identifying descriptions or placeholders where useful. Keep private runtime configuration outside the repository.
- Before saving any memory, check sensitivity, accuracy, explicit exclusions, duplication, and conflicts. If sensitivity is uncertain, omit the detail and ask for clarification before publication. Preserve unrelated memories, distinguish confirmed facts from uncertainty, and do not turn temporary overrides into standing preferences.
- These shared rules apply to all current and successor agents through the mandatory root policy. Respect platform approval gates for every write and report persistence as pending or blocked until it succeeds. Repository policy alone does not provide access to other agents, automatic future loading, or continuous synchronization.

## Managed files and reporting

- Edit and add managed files here; the user's live Codex, Copilot, VS Code, and helper paths are symlinks into this checkout.
- Locate this checkout from the directory containing the setup script (`setup.sh` on Linux/WSL, `setup.ps1` on Windows), rather than assuming a fixed home-directory path.
- The setup script (`setup.sh`/`setup.ps1`) installs Python requirements where applicable and checks external runtime tools; avoid adding system packages or agent CLIs unless explicitly requested.
- Keep the README's file map and setup instructions current.
- Keep `.github/workflows/super-linter.yml` aligned with every language and executable/configuration format used in the repository. When adding one, enable its Super-Linter validator, add necessary linter configuration, update the README's lint coverage, and verify the new lint check.
- At the end of every user query, each agent must record its own current quota through its existing status helper and `track_agent_usage.py`; retain the generated forecast and any warning in the local `.agent-usage.jsonl` report, and include warnings in both the final response and completion/status email. This data file must remain ignored and never be staged or published.
- Timestamp every user-facing step in CLI and VS Code progress/final responses and every material step in completion/status emails, using the actual local time. Include a footer in every such response and email with available SSH-agent key fingerprints (never key material), the answering agent's own quota usage/remaining and renewal/reset time, and any forecast warning projecting exhaustion before local midnight. State when a forecast is unavailable; do not report another agent's quota or expose authentication tokens.

## Git changes

- Use the machine's global SSH transport preference for Git remotes; do not change a remote to HTTPS.
- Before committing, inspect the complete diff and scan tracked changes for credentials, private keys, personal/work recipient addresses, SMTP relay hostnames, and internal-only details. Keep machine-specific values outside tracked files.
- Run relevant tests before publishing changes. Never commit user runtime state, local authentication/configuration files, or tool caches.
- When coding, work in a task-specific branch, do as small tasks as possible at once, maintain a WIP/TODO status file for failsafe resumes, and push after each successful task. Before creating a PR/MR, remove the WIP/TODO status file and squash commits as needed so the PR/MR presents a clean final history (keep one final commit where supported). Before rewriting a remote branch, verify its expected state, preserve a recovery reference when useful, and use an explicit `--force-with-lease`.
- For pull requests, use one final commit and write a concise reviewer-focused overview covering the problem, resulting behavior, validation, and limitations.
- Push changes upstream when requested or required by the applicable global agent instructions.

## Terse files and truncation-safe edits

- Write status, TODO, memory and instruction files with as few words as possible while keeping the full meaning: cut filler, repetition and history that no longer matters; keep facts, IDs, numbers and decisions.
- Tools may return only the first part of a large file (about 40 KB) and may write only whole files. Always work around this risk. Before editing, compare the size from the directory listing with what you received. If the read looks cut off or the sizes differ, read the rest first (raw URL at a commit SHA, in parts, or a clone). Never push a file built from a partial read.
- Keep each agent-edited file under 30 KB; split a larger one by topic so one read gets all of it.
- After a push, check the new size and the end of the file.
