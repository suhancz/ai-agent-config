# All-agent contract: lint-compliant writing

Part of the all-agent contract in [all-agents.instructions.md](all-agents.instructions.md). Read it on every request together with that file.

## Writing lint-compliant changes in advance

- Every current and successor agent finds out, before it writes or changes a file, which linters, formatters, spell checkers, wording or natural-language checkers, type checkers, and static analyzers the affected code base uses, and writes the format and wording that satisfy them in advance. Do not write first and wait for a lint job to report the problems.
- Find them in the repository itself: the lint and CI workflows, linter configuration files and directories (for example `.github/linters/`, `.editorconfig`, `.yamllint`, markdown lint configuration, `pyproject.toml`, `eslint.config.*`, `.ansible-lint`, `.codespellrc`), ignore files, pre-commit configuration, package manifests, Makefiles, CI scripts, and the repository's own instructions. Note which validators are enabled and which are switched off or restricted, and read the published lint logs of earlier runs for the rules that actually fail.
- Read the configured rules for the type of every file being changed and apply them to the whole change, not only to a line that a linter reported: formatting, indentation, line length, line endings, final newline, import order, naming, quoting, fully qualified names, spelling, and the terms that wording checkers reject. When the configuration says nothing, match the neighboring files and the common style of the language. Read the lessons already recorded in the linter-lessons section of the shared memory file and apply them as well.
- Detect the configured linters again, locally, just before every push, on the freshly fetched base and working branches. Other commits, merges, bots, or the user may have added or changed linters since the first look. Run every linter found this way on the files changed for the push, including newly added ones, and fix all complaints before pushing, as the linting-before-push rule in the [required behavior](all-agents.instructions.md#required-behavior) requires.
- When a linter is referred to as `latest`, a floating tag, a branch, or without a version, resolve the version that actually runs: read the workflow or configuration, the image or package tag, and the published release notes or defaults of that version. Compare what that version contains and expects, such as its enabled rules, changed defaults, new validators, and removed options, with the configuration of the repository, and adjust the code accordingly before the real push. State the resolved version in the report, and say when it could not be resolved.
- When a configured linter is not available locally, first apply the installation steps of the linting-before-push rule in the [required behavior](all-agents.instructions.md#required-behavior). When it cannot be installed automatically, because it needs a permission, a network, or a container runtime that is missing, suggest to the user that it be installed, with the exact command or image for the resolved version, and continue with the next step without waiting.
- When a linter stays unavailable, for example because the agent works only through a repository connector, find its source code, documentation, rule list, default configuration, and release notes for the resolved version, and mimic its behavior: check every changed file against the configured rules by hand, or with a helper script when the check is too large or too repetitive to do reliably by hand, and fix what the mimicked check finds. Report the linter as mimicked and not run, name the sources used, and never claim a lint pass without a real lint run. The CI job is then the first real run, and its result must be read.
- Save every helper script that mimics a linter in the repository being worked on, in the place that its conventions use for helper scripts, and reuse an existing mimic helper before writing a new one. Give it an interpreter shebang, add its exact path to the executable manifest, and record Git mode 100755 in the same task, as the [executable-intent section](all-agents-scripts-and-quota.instructions.md#executable-intent-and-all-agent-script-maintenance) requires; a repository that has its own executable-permission mechanism uses that mechanism instead. Let the helper read the repository's linter configuration and apply the rules of the resolved version instead of hardcoding a copy of them, and add a test where the repository has a test convention. A helper mimics a linter and never replaces a real lint run.
- Keep these helper scripts up to date on linter detection. Whenever the detection step finds a linter that was added, removed, renamed, or changed in version or configuration, update the helper and its test in the same commit as the change that exposed it, and remove what no longer applies. Compare the helpers with the detected linters just before every push, together with the other detection step, and report a helper that could not be brought up to date.
- Do not hide a finding with an ignore entry, a disabling comment, or a weaker configuration to satisfy a linter, unless the user decided that. Rewrite the content instead, or report the finding with its cause.
- Keep learning from linter outputs. After every lint run, local or CI, read the real output, including warnings and notices, and extract each lesson that would have avoided a finding or that shows how the linter or its resolved version behaves. Record every generic, non-sensitive lesson in the shared memory file memory/MEMORY.md, in its section for lessons from linter outputs: one concise bullet with the linter, its version when known, and the rule or behavior, without file names, project names, or other identifying details, and deduplicated against the existing entries. Record a lesson that is specific to one repository in that repository's own instructions or memory file instead, and update the mimic helpers for it. Record the lesson in the same commit as the fix that taught it, or in the next commit when the output arrives later, and report what was learned and where it was recorded. Never record a lesson from a guess, only from an actual linter output or from the linter's documentation. When the memory file cannot be written, report the lesson as pending, as the learning rules in the shared memory require.
- When no linter is configured, follow the common style of the language and of the neighboring files, and say that none was found.
- This applies to every file an agent writes, including documentation, instruction files, status files, workflow files, and commit messages when the repository checks them, in every repository and project, including those whose own instructions do not mention it.
