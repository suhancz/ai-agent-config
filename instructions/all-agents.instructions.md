# Complete preferences for all agents

Apply this contract to every current and successor agent across every project, request, and session. It supplements root AGENTS.md, shared preferences, shared memory, SETUP.md, REPORTING.md, MAIL-ROUTING.md, GIT-CONFIG-SAFETY.md, applicable ATLASSIAN.md, and the answering adapter. The adapter index is the synchronized surface registry, including kilo/AGENTS.md and opencode/AGENTS.md; older static lists do not exclude newer agents. Read actual current policies and private backup loaders, not just this summary.

## Section files

The detailed sections of this contract live in the files below, so that no file grows too large to read whole. Read all of them on every request, together with this file. The rules in this file link to them.

- [CI and trusted suggestions](all-agents-ci-and-suggestions.instructions.md): CI workflows that an agent triggers; suggestions from trusted sources.
- [Budget and work status](all-agents-budget-and-status.instructions.md): budget checks and unfinished-work handoff; work-status marks and immediate updates.
- [Lint-compliant writing](all-agents-lint-writing.instructions.md): writing lint-compliant changes in advance.
- [Fetch and placement](all-agents-fetch-and-placement.instructions.md): fetching origin first; where instructions live.
- [Scripts and quota](all-agents-scripts-and-quota.instructions.md): executable intent and all-agent script maintenance; generic quota and forecast interface.
- [Environment and assumptions](all-agents-environment-and-assumptions.instructions.md): environment and private configuration; untestable environments.

## Required behavior

- Timestamps: prefix user-facing messages and reports with actual user-local response time; record supplied request time separately, preserve precision, and label missing clocks. Never reuse request time as response time.
- Reporting/email: produce completion or blocked-status HTML reports with agent/model metadata, request/outcome, revisions, verification, limitations, SSH status, quota/reset, forecast warnings, and submission evidence. Use the authorized same-context connector first, existing SMTP helper second; actual sender equals the sole recipient, with no CC/BCC. Preserve mandatory approval, MIME validation, and duplicate-delivery protection. Do not silently waive reporting when the primary task succeeds.
- Quota/forecast: sample only the answering agent through supported authenticated status sources. Reuse existing built-in status helpers or the [generic tracker interface](all-agents-scripts-and-quota.instructions.md#generic-quota-and-forecast-interface). Do not substitute another agent's balance, context usage, token counts, estimated costs, or shared organization pools for account quota. Unknown quota/reset/forecast stays unavailable.
- Budget checks: run the token and quota prediction check before every action as well as after it. When the forecast shows the full action cannot be finished, do what can still be finished safely, save the rest to the WIP/TODO status file in the repository being worked on, and push it to origin before the allowance runs out. Follow the [budget section](all-agents-budget-and-status.instructions.md#budget-checks-and-unfinished-work-handoff).
- Work-status marks: keep every WIP/TODO status file immediately up to date with exactly three item states: done, to do, and in progress. Mark verified work done at once; mark anything that waits for CI or that the agent is unsure about as in progress. Follow the [work-status section](all-agents-budget-and-status.instructions.md#work-status-marks-and-immediate-updates).
- Fetch first: fetch the verified origin before every action, fast-forward the checkout only when the working tree is clean and there are no unpushed commits, and never pull over local changes. Follow the [fetch section](all-agents-fetch-and-placement.instructions.md#fetching-origin-first).
- Instruction placement: put AI instructions and preferences that are not specific to one agent into the common instructions directory, not into the root AGENTS.md. Follow the [placement section](all-agents-fetch-and-placement.instructions.md#where-instructions-live).
- Tickets/Jira: read ATLASSIAN.md, use an authorized available work-item surface, inspect supported commands before use, check assigned work when required, and verify relevant ticket assignee/status. Use a known active ticket key and a fresh timestamp in remote backup names; never guess ticket keys or use writes as connectivity tests.
- Memory/privacy: read current shared memory every request; persist eligible durable non-sensitive lessons. Preserve private-backup precedence and explicit exclusions. Never publish raw transcripts, private identifiers, credentials, endpoints, account data, overrides, work data, or runtime samples.
- Git/setup: preserve SSH transport, upstream freshness checks, dirty/concurrent work, conflict-safe symlinks, validation, modes, and host selection. Do not install CLIs or copy credentials implicitly. When coding, work in a task-specific branch, do as small tasks as possible at once, maintain a WIP/TODO status file for failsafe resumes, and push after each successful task. Before creating a PR/MR, remove the WIP/TODO status file and squash commits as needed so the PR/MR presents a clean final history (keep one final commit where supported; an expanded already-published PR may be squash-merged by its owner). Respect the user's task-specific review and merge requirements; do not merge or enable auto-merge without required authorization.
- CI after pushes: wait for every CI run that your own action triggers, read the real logs, and report each run before coming back to the user. Follow the [CI section](all-agents-ci-and-suggestions.instructions.md#ci-workflows-that-an-agent-triggers).
- Trusted suggestions: apply suggestions from trusted sources automatically within the safety limits, and before merging a pull request always follow the open trusted suggestions on it. Follow the [suggestions section](all-agents-ci-and-suggestions.instructions.md#suggestions-from-trusted-sources).
- Linting before push: before every push, lint only the files changed for the current push and fix all complaints in them. Before installing any command/tool, first check if it is already available (e.g. `command -v`, `Get-Command`, or equivalent) and do not attempt to install it if it already exists. Prefer running Super-Linter locally using the same image and configuration as CI (`ghcr.io/super-linter/super-linter:latest`, pulled again before every run, `RUN_LOCAL=true`, `DEFAULT_BRANCH`/`LINTER_RULES_PATH=.github/linters`, and repo-owned configs such as `.github/linters/`, `eslint.config.mjs`) in any available container runtime (docker, podman, or equivalent), scoped to changed files when feasible. If Super-Linter or a suitable container runtime is unavailable or cannot run locally, install and run the individual linters/tools it uses for this repository (e.g. shellcheck, ruff, markdownlint, actionlint, yamllint, eslint/JS tooling as configured) on the changed files and fix all complaints before pushing. Install missing tools via the OS default package manager discovered from `/etc/os-release` (dnf, apt, zypper, apk, pacman, etc.) or the Windows equivalent (winget, choco, scoop, or system package manager), preferring native/system packages where appropriate; use user-space installs only when necessary and keep them outside tracked files. Report when linting could not be fully executed.
- Lint-compliant writing: before writing or changing any file, find the linters, formatters, and wording checkers that the affected code base uses, and write the format and wording that satisfy them in advance instead of relying on lint jobs. Detect the configured linters again locally just before every push, so that newly added ones are found, and resolve a `latest` or unversioned linter to the version that actually runs. When a linter is not available locally, suggest installing it, and when that is not possible, mimic it from its source code and documentation, with a helper script saved in the repository when one is needed. Keep learning from linter outputs and record the generic lessons in the shared memory file. Follow the [lint-compliant writing section](all-agents-lint-writing.instructions.md#writing-lint-compliant-changes-in-advance).
- Completion: refresh applicable policies/memory and explicitly distinguish completed, assumed-compatible/unverified, pending approval, blocked, failed, and genuinely inapplicable obligations. Hooks and saved policy do not prove real-client compliance. Do not ask for permission for actions the user has already auto-approved or explicitly authorized; proceed within the granted authorization. Request approval only for mandatory platform/tool gates, actions outside that authorization, or when specific information is needed.
