## All-agent message and request timestamps

- Every current and successor agent must prefix every assistant-authored user-facing message with a timestamp in the user's local timezone. This includes all chat surfaces, Projects, CLI and IDE sessions, progress/commentary updates, final answers, approval questions where editable, and completion or blocked-status reports. It is not limited to CLI or VS Code. This shared rule supersedes narrower or host-timezone-based wording in agent entry instructions.
- Use `[YYYY-MM-DD HH:MM:SS TZ (UTC+/-HH:MM)]` when that precision and timezone offset are available. Obtain the actual response time immediately before composing or sending the message. Resolve the user's timezone from explicit context or private runtime configuration; account for daylight-saving transitions. Do not substitute the server's or runner's timezone merely because it is the machine default. Keep any user-specific timezone/location setting private rather than hard-coding it in tracked policy.
- Timestamp each user request as well. Capture the supplied transport/query timestamp when available, preserve its actual precision, convert it to the user's timezone when necessary, and label it as request time. Include it in the first acknowledgment or response for that request and alongside the original request in completion/status reports. Agents cannot rewrite original user chat messages; annotating requests in their own responses and reports does not claim to alter the platform transcript.
- Request, receipt, response, operation, completion, commit, and email-submission times are distinct. Do not reuse request time as response time or describe a commit timestamp as the time of an uncaptured operation. If only local receipt time is observable, label it receipt time and state that the original request timestamp is unavailable. If only minute precision is supplied, do not invent seconds.
- If a reliable current clock or the user's timezone is unavailable, retain the timestamp field and explicitly label what is unavailable. A supplied request timestamp may be shown as request time, never passed off as a freshly sampled response time. Never invent timestamps, timezone offsets, operation durations, or historical step times.
- Begin report bodies, including HTML reports, with the actual preparation/response timestamp and timezone when available. Include the request time, individually captured material-step times, and completion time. Mark unavailable times explicitly; timestamps embedded in the original request or source artifacts must retain their original meaning. Preserve identical approved sender/recipient identities, mandatory send approvals, privacy rules, and the existing report checklist.
- Apply this policy to successor agents and synchronize affected instructions when necessary. Platform-generated messages or uneditable approval/tool UI are outside an agent's formatting control; do not falsely claim those were changed. Persist generic timestamp behavior and non-sensitive preferences, not private request transcripts or identifying location/timezone metadata.

## Git changes

- Use the machine's global SSH transport preference for Git remotes; do not change a remote to HTTPS.
- Before committing, inspect the complete diff and scan tracked changes for credentials, private keys, personal/work recipient addresses, SMTP relay hostnames, and internal-only details. Keep machine-specific values outside tracked files.
- Run relevant tests before publishing changes. Never commit user runtime state, local authentication/configuration files, or tool caches.
- Keep task changes in one final commit. Before rewriting a remote branch, verify its expected state, preserve a recovery reference when useful, and use an explicit `--force-with-lease`.
- For pull requests, use one final commit and write a concise reviewer-focused overview covering the problem, resulting behavior, validation, and limitations.
- Push changes upstream when requested or required by the applicable global agent instructions.
