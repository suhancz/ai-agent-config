# Shared reporting

Apply root [instructions](AGENTS.md), [mail routing](MAIL-ROUTING.md), [shared memory](memory/MEMORY.md), and the answering adapter's capability limits. These generic rules are shared; product-specific quota commands belong in adapter documentation.

## Universal AI scope and standing reporting authorization

These preferences apply to every AI assistant and agent the user uses, regardless of provider, product, coding capability, integration name, project, folder, workspace, conversation, or session, including future systems. Named adapters are implementation examples, not a restriction of scope.

The user gives standing authorization to send required completion and blocked-status emails automatically whenever a supported authenticated delivery capability and platform permissions allow it. Do not ask an additional discretionary approval, recipient-choice, or confirmation question merely to send these required reports. This is the default behavior, not an opt-in offered at each task. Derive the recipient from the actual sender as specified below. This authorization does not cover unrelated emails or additional recipients.

Mandatory platform or tool approval gates remain binding and are not disabled by this preference. Where exact-target/message approval is compulsory, use that gate with the full resolved draft and explain that it is a platform requirement, not a request to renew standing consent. Do not route around a gate or claim unattended delivery is enabled when it is not. Missing delivery capability must be reported as a specific blocker, not converted into a discretionary request for consent.

Every AI must load the full applicable repository configuration from the local filesystem when accessible; if the local clone or required files cannot be read, retrieve the canonical sources through authorized Git access or a repository connector. Follow [the shared loading policy](SETUP.md#configuration-loading-for-every-agent), including revision checks, linked policies, private override boundaries, and explicit failure reporting. This fallback applies to all AI systems, not only the named agent adapters. Repository policy does not itself configure inaccessible applications or prove universal enforcement.

## Agent, model, and consistent reporting metadata

Every current and successor agent must include its answering agent identity and model identity in chat reports, completion/status email, and Git commit messages it creates. Include available product/client version and model version or execution mode when reliably exposed and permitted. Keep agent/product identity distinct from model identity; do not guess an underlying model from a product name, account, token, another agent, or unsupported inference. Use the identity the platform permits the agent to disclose; explicitly mark unavailable version or mode details rather than inventing them.

For every AI, report the most specific supported model information rather than using the assistant or product name alone as a substitute for unavailable backend details. Use clearly separated fields for Agent, Model, and Model version/mode. When a supported interface or user-provided evidence shows an automatic model-selection mode, include its exact label and meaning, explicitly identifying it as a selection mode rather than a verified backend model. For example, a verified selection label may be reported as 'Model: Best (selects the best available model; selection mode, backend unidentified)'. Do not apply this example universally or invent a mode. If platform-required identity wording differs, retain it and add a separate observed-selection field. State the source and freshness limits of UI or user-provided evidence; a past screenshot does not verify the current selection. For each unavailable model, version, or mode detail, explain the concrete reason, such as the interface not exposing a verifiable backend identifier. Distinguish unknown from known-but-not-disclosable information without revealing protected details. Never assert that all models in a menu participated, infer a specific backend from a routing label, or present a product identity as proof of a backend version. Apply this specificity and explanation rule equally to chat, email, and Git commit messages, subject to privacy and platform constraints.

Apply the user's other applicable reporting preferences consistently across these surfaces: user-local timestamps with request and response/operation times distinguished, outcome, changed files/revisions where available, verification and unrun tests, limitations, pending requirements, and available own-agent quota/reset/forecast and SSH-fingerprint access status. A concise chat or commit metadata block may summarize these fields; an HTML email retains the full required report. Do not publish private runtime settings, addresses, account identifiers, credentials, private paths, raw transcripts, or identifying SSH fingerprints in public commits. State that sensitive details are withheld there while retaining allowed private reporting. Never fabricate unavailable metadata or drop a requirement silently.

Put agent/model metadata in a Git commit message body or trailers, not by changing the user's Git author/committer identity. Include only information known before the commit; report the resulting commit SHA and actual submission/delivery evidence afterward in chat and email. Preserve the single-commit workflow and mandatory approval: do not amend an already approved message or rewrite history merely to add newly observed metadata without fresh authorization. For progress updates, keep metadata concise and reuse the latest valid status sample with its sample time. Platform-generated or uneditable UI is outside the agent's control; report that limitation rather than claiming it was modified.

## Completion and status email

At every completed task, send the required HTML completion report; for blocked/incomplete execution, send a status report when the delivery capability exists. Resolve the context and approved private reporting identity under mail routing. Sender and recipient must be identical. Do not silently substitute an account default or move work data to a personal route. Standing consent does not bypass mandatory exact-target/message approval. Present a pending report when a gate requires approval rather than silently omitting it.

For every current and successor agent, always derive the report recipient from the resolved actual sender address. Once the appropriate authenticated sender is established under mail routing and current user instructions, use that exact address as the sole report recipient; do not ask for a separate recipient merely because no independent recipient setting exists. Preserve the full address, including any plus tag, and do not add CC/BCC recipients. A configured report address remains an identity constraint, not permission to send from one address to another. Resolve genuine sender/context conflicts before sending and retain mandatory exact-message approval. Keep actual addresses and connector identities outside the repository.

Prefix messages and report bodies with the user's actual local timestamp and timezone. Record the supplied request timestamp, captured material steps, and completion time separately; mark missing clocks/precision rather than inventing them. Include the original request with needed redaction, detailed outcome, changed files/revisions, verification and unrun tests, errors, limitations, warnings, relevant links, SSH fingerprints only, own-agent quota/reset status, and actual submission evidence.

Prefer an appropriate already authenticated connector; retain the same-context SMTP fallback. Never retry via a second transport after an uncertain submission until duplicate-delivery risk is resolved. Distinguish accepted submission, a saved Sent copy, verified inbox delivery, and verified rendering.

## Private SMTP fallback

The fallback uses helpers/send-completion-report.py and `/usr/sbin/sendmail`. The local report-address file defaults to `$HOME/.config/ai-agent-config/report-address`; restrict it to mode 0600. Override its path with AI_AGENT_REPORT_ADDRESS_FILE. Without the file, the helper uses the current user's outgoing mapping in /etc/ssmtp/revaliases, then the configured root mailbox in /etc/ssmtp/ssmtp.conf. Apply stricter identity constraints from current instructions; keep relay configuration and addresses private.

Invoke the helper with Python 3.12 and its prepare, validate, and send commands. Prepare a concise subject and nonempty visible HTML body. Require MIME-Version 1.0, text/html with UTF-8, 8bit transfer encoding, a valid header/body separator, canonical CRLF without doubled carriage returns, and lines no longer than 998 octets. Never apply curl --crlf to prepared MIME. The helper validates CRLF, converts to LF for local sendmail, and requires the canonical explicit queued SMTP response: 250 2.6.0 explicitly stating queuing. Do not invent that evidence for an opaque connector result or claim raw-MIME compliance when a connector's encoding cannot be inspected.

A reported empty message requires MIME/upload-path validation before an authorized corrective send. A failed Sent-copy operation after successful sending is not a reason to resend.

## Own-agent status and private usage tracking

Identify the answering agent. Run ssh-add -l when supported and permitted; list fingerprints only, never key text. Distinguish an inaccessible agent from an empty one. Use only a documented authenticated quota interface for the answering agent, never another agent's helper, secrets, API-key decoding, or context-window usage. Report unavailable quota/reset/forecast rather than fabricating them. Adapter documents contain supported commands and exact fallback lines.

At query end, refresh the agent's supported quota sample and record it through helpers/track_agent_usage.py only for a supported agent identifier. The tracker currently accepts two adapters, documented in their guides. Do not pass unsupported names. Keep .agent-usage.jsonl private, ignored, and never staged. Include generated forecast warnings in final responses and reports. For progress updates reuse the latest own-agent sample with its sample time rather than making redundant status queries.

Forecasts require two same-day samples at least five minutes apart. A detected replenishment starts a new trend. Linear-depletion estimates can warn about exhaustion before user-local midnight but cannot predict future workload changes or unobserved resets. Report insufficient data or unavailable recording honestly. The current agent's exact quota-status line remains the final line when available.
