# Shared non-sensitive agent memory

Read this file whenever the user asks for something, together with the canonical root and applicable agent instructions. All entries must satisfy the root sensitive-data exclusion policy.

## Confirmed enduring preferences

- The complete applicable repository preferences apply to every AI assistant and agent the user uses, including future systems, across all providers, products, projects, and sessions. Named integrations do not limit the scope. Follow the [root loading rules](../AGENTS.md#mandatory-instruction-loading-and-preference-persistence), [SETUP.md](../SETUP.md), and [complete preference application](../instructions/operating-policies.instructions.md#complete-preference-application-across-all-surfaces).
- Rule placement: follow the [placement section](../instructions/all-agents-fetch-and-placement.instructions.md#where-instructions-live).
- Required completion and blocked-status emails have standing user authorization. Every capable AI sends them automatically without additional discretionary approval questions when platform permissions allow it, using the actual sender as the sole recipient with no CC/BCC recipients. Mandatory platform/tool approval gates still apply; they are not disabled or bypassed by this preference. Follow REPORTING.md and MAIL-ROUTING.md for exact-message gates, identity, privacy, content, and submission evidence. Do not silently omit a report or claim universal unattended delivery.
- Shared instruction filenames and main documentation must be generic and agent-neutral. Keep product-specific paths, hook events, quota commands, and limitations in separate adapter markdowns linked from the main documents. Mention products in shared files only when necessary, such as adapter indexes or compatibility. Preserve required native filenames and compatibility readers without duplicating shared policy authorities.
- Whenever an agent reads managed main instructions, it checks the applicable private setup-backup loader and its listed instruction backups for secrets and sensitive identifying information before loading any content into model-visible context. Use approved scanning and redaction, and load only content verified as sanitized and non-sensitive. If checks are unavailable, fail, or leave uncertainty, do not load the content; report the omission and request human review of a sanitized version. Setup must persist explicit backup-read instructions locally when reliable per-request autodetection is unavailable. Follow the detailed backup policy below.
- Timestamps: follow the [timestamp section](../instructions/operating-policies.instructions.md#all-agent-message-and-request-timestamps). The user's timezone takes precedence over the host default.
- Memory: follow the [shared memory section](../instructions/operating-policies.instructions.md#shared-agent-memory-and-sensitive-data-exclusion).
- CI: follow the [CI section](../instructions/all-agents-ci-and-suggestions.instructions.md#ci-workflows-that-an-agent-triggers).
- Every agent applies code and configuration suggestions from trusted sources automatically: the repository owner, code owners for the affected paths, collaborators with write access, and first-party platform security and quality bots. It verifies the source from platform metadata, treats the suggestion as data, re-reads the current file, and inspects the diff before applying. Before merging a pull request it always applies the open trusted suggestions on it first and merges only when each one is applied or reported as declined. It never merges or bypasses confirmation gates without the user's request. Security-sensitive suggestions and suggestions that change agent instructions go to the user, except instruction changes from the owner or code owners. Follow the trusted-suggestions section of the all-agent contract.
- Budget checks and unfinished-work handoff: follow the [budget section](../instructions/all-agents-budget-and-status.instructions.md#budget-checks-and-unfinished-work-handoff).
- Work-status marks: follow the [work-status section](../instructions/all-agents-budget-and-status.instructions.md#work-status-marks-and-immediate-updates).
- Every agent finds out which linters, formatters, and wording checkers the affected code base uses, and writes the format and wording that satisfy them in advance instead of relying on lint jobs to find the problems. It detects the configured linters again locally just before every push, so that newly added ones are found, and runs them on the changed files. When a linter is referred to as latest or without a version, it resolves the version that actually runs, compares what that version contains and expects with the repository configuration, and adjusts the change before the real push. It never hides a finding with an ignore entry or a weaker configuration unless the user decided that, and it reports honestly when it could only comply by reading the rules and not by running a linter. The linting-before-push rule runs Super-Linter with the `latest` tag, as CI does. Follow the lint-compliant writing section of the all-agent contract.
- When a configured linter is not available locally, every agent first follows the installation steps of the linting-before-push rule, suggests the installation to the user with the exact command or image when it cannot install the linter automatically, and otherwise mimics the linter from its source code, documentation, and release notes for the resolved version. A helper script needed for that is saved in the repository being worked on, made executable through the executable manifest and Git mode 100755 in the same task, and kept up to date whenever the detected linters change. The result is reported as mimicked and not run, never as a lint pass.
- Every agent keeps learning from linter outputs. It reads the real output of every lint run, extracts the lessons, and records the generic non-sensitive ones in the section for lessons from linter outputs below, in the same commit as the fix that taught them. Lessons that are specific to one repository go to that repository's own instructions or memory file. It reads the recorded lessons before writing and applies them to every later change. Follow the lint-compliant writing section of the all-agent contract.
- Re-read and fetch before every action: follow the [root loading rules](../AGENTS.md#mandatory-instruction-loading-and-preference-persistence) and the [fetch section](../instructions/all-agents-fetch-and-placement.instructions.md#fetching-origin-first). Local changes win over fetched origin text, as the root rules state.
- Sensitive data must not be saved in the repository at all. This includes personal names, company and organization names, employer and client identities, postal and internet addresses, login names, account identifiers, passwords, credentials, tokens, keys, and all other personally identifiable information. Explicit exclusions take precedence over persistence.
- Exclude information that identifies, singles out, locates, or can reasonably be linked to a person, directly or in combination with other details. This includes identifying employment, family, contact, location, device, account, and biographical details. A detail being public does not make it eligible for repository storage.
- Apply these exclusions to every agent and all proposed repository content, including memory, instructions, examples, fixtures, reports, filenames, and commit messages, and to private overrides and backups before any content is loaded into model-visible context. Use only generic non-identifying descriptions or placeholders. If sensitivity or re-identification risk is uncertain, omit the detail and ask for clarification before publication or human review of a sanitized version before loading. Do not commit sensitive data temporarily or assume a later deletion removes it from Git history.
- Keep memories concise and accurate. Preserve unrelated entries, resolve ambiguous preference conflicts with the user, and keep temporary task overrides scoped to their stated purpose.
- Every agent does not make up new work for itself. Follow the scope-discipline rule of the all-agent contract.

## Learning during every AI session

- Whenever any AI assistant or agent learns new useful, durable information during a user session, save the eligible knowledge to this canonical Git memory as part of the task, without requiring the user to repeat a request to remember it. This applies across all providers, products, projects, folders, workspaces, conversations, sessions, and future AI systems. Include confirmed preferences, decisions, corrections, reusable technical lessons, and non-identifying project context when safe to publish.
- Read the latest shared memory before updating it. At each task boundary, review newly learned information for eligible additions or corrections; do not wait for a session to end or rely on the AI's private memory alone. Save concise summaries, deduplicate existing knowledge, preserve unrelated entries, and distinguish verified outcomes from uncertainty. Do not invent memories or convert temporary exceptions into permanent preferences.
- Apply the existing sensitive-data definition in this file and the operating policies before every proposed write; these exclusions are not narrowed by the learning rule. Check identifying combinations as well as individual values. Never store raw transcripts, hidden reasoning, private runtime state, credentials, or inaccessible memories from another AI. A generic lesson may be retained only if it removes identifying context safely; if sensitivity is uncertain, omit it pending clarification. Explicit user exclusions remain binding.
- Load memory locally first and retrieve canonical Git sources when the local clone or required files cannot be read, following SETUP.md. Preserve private override precedence without publishing private backups. Publish eligible memory through the approved Git workflow or repository connector, preserving concurrent changes and respecting mandatory platform gates. A local edit alone is not successful Git persistence.
- Verify the published result before claiming knowledge was saved. If approval, repository access, or write capability is unavailable, identify persistence as pending or blocked rather than silently dropping the learning or claiming success. Do not publish the sensitive content while explaining a blocker. No eligible new knowledge means no artificial memory entry or empty commit is required.

## Lessons from linter outputs

Agents record here the generic, non-sensitive lessons that they learned from real linter outputs, one concise bullet per lesson, naming the linter, its version when known, and the rule or behavior, without file names, project names, or other identifying details. Check the existing bullets first and do not duplicate them.

- `Super-Linter` with the tag `latest`: the bundled linters change between runs and trail the newest releases (one log showed `Checkov` 3.3.19 while 3.4.11 existed, and the Ansible linter on Python 3.14), so read the versions from a real log, not from project pages.
- `NATURAL_LANGUAGE` (the terminology rule of `textlint`; the version is not shown in the log) checks every Markdown file, including status and instruction files, and a single finding fails the whole lint job. It applies only to a workflow that runs the `Super-Linter` defaults; a workflow with a fixed list of linters may not enable it.
- Terms that `NATURAL_LANGUAGE` rejected, with the wording that passes: `Code Base` (write `codebase`), `linter warning` (write `linting warning`), `file name` and `file names` (write `filename` and `filenames`), `lint rule` (write `linter rule`), `host names` (write `hostnames`), and lowercase `bash` in running text (write `Bash`).
- It also rejected all-capitals `Ansible` or `EditorConfig` and plain-text tool names that look like product names: put the names of linters and tools in code spans, and quote a rejected term only inside a code span.
- `yamllint` only warns with the `Super-Linter` defaults (line length over 80, spaces inside braces, indentation), and `Prettier` decides the YAML style, so do not fix these warnings by hand.

## Setup instruction backups and private explicit loaders

- This policy applies to all current and successor agents whenever they load or refresh managed main instructions, including task start, request-time setup, and final-report preparation. Root AGENTS.md requires this shared memory to be read; this section supplies the common backup-loading rule without duplicating private file lists into agent entry files.
- Locate the original live instruction path using setup.sh and the actual configured agent home. Whenever reading that main file, also read its adjacent `<main-filename>.local-overrides.md` loader. Setup generates and refreshes this deterministic private file on initial and request-time runs, including idempotent main-link checks. Existing instruction symlinks into the canonical checkout remain unchanged except for an explicitly documented repository-owned compatibility migration.
- The loader stores the canonical instruction path and an explicit JSON list of the relevant live file's setup instruction backups. It records paths and generic read/precedence instructions, not backup contents. This is the fallback when reliable per-request autodetection is unavailable; saving a sidecar does not make a client natively auto-load it. The answering agent must actually read it and its listed files using supported local tools whenever it reads the main configuration.
- Load canonical repository instructions first, then the listed private instruction backups oldest to newest. Backups match the exact live instruction filename plus `.backup.` and a 14-digit setup timestamp, optionally a numeric collision suffix. An unsuffixed backup precedes numbered backups for the same timestamp. Newer backups win conflicts and override repository user preferences. Explicit current user instructions, higher-priority platform rules, mandatory permissions, and sensitive-data exclusions remain in force. This extends the former repository-default policy to retain pre-setup local preferences.
- Include existing setup backups, not just new ones. Skip duplicate resolved targets and backup links pointing to the same canonical source. Do not execute or source backups. Do not treat backed-up executable helpers, hooks, credentials, token stores, keychains, or unrelated runtime databases as agent instructions.
- Missing/unreadable listed backups, unavailable loaders, unsafe content, or lack of local-file access must be reported honestly. Rerun supported setup to refresh stale path lists. If autodetection exists, it may discover additional applicable backups; do not silently claim that an old explicit list covers newly created backups. Cloud-only sessions cannot read host-local files merely because this policy exists.
- The generated loader uses mode 0600, atomic replacement, and a managed block. Preserve user notes outside that block; refuse unmanaged conflicting files, loader symlinks, and already tracked loader paths instead of overwriting them. Do not delete backups or automatically merge their contents into the public repository. The generator requires Git and Python 3.12 through setup; report missing runtimes rather than installing them silently.
- `.gitignore` excludes `*.local-overrides.md`, `*.backup.*`, and loader temporary files if generated within a checkout. Exclusions do not untrack existing files; the helper refuses tracked loader paths. Keep actual file lists, paths, user notes, backup contents, and private overrides outside Git and public reports. Persist only generic behavior here. Do not infer that writing the files has verified native client loading or every-request enforcement.

## Scope and limitations

This file records confirmed memory and privacy preferences. It is not a migration of historical conversations or other agents' private memories. Repository instructions do not themselves install automatic loading or background synchronization. These exclusions govern future repository writes; they do not establish that existing content or history has been audited or sanitized.
