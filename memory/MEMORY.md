# Shared non-sensitive agent memory

Read this file whenever the user asks for something, together with the canonical root and applicable agent instructions. All entries must satisfy the root sensitive-data exclusion policy.

## Confirmed enduring preferences

- The complete applicable repository preferences apply to every AI assistant and agent the user uses, including future systems, across all providers, products, projects, folders, workspaces, conversations, and sessions. Named integrations do not limit the scope. Every AI reads the configuration from the local filesystem when accessible; if the local clone or required canonical files cannot be read, it retrieves the canonical Git sources through authorized Git access or a repository connector. Follow SETUP.md, preserve accessible private override precedence, identify the revision used, and report missing private files or failed retrieval rather than claiming compliance.
- Required completion and blocked-status emails have standing user authorization. Every capable AI sends them automatically without additional discretionary approval questions when platform permissions allow it, using the actual sender as the sole recipient with no CC/BCC recipients. Mandatory platform/tool approval gates still apply; they are not disabled or bypassed by this preference. Follow REPORTING.md and MAIL-ROUTING.md for exact-message gates, identity, privacy, content, and submission evidence. Do not silently omit a report or claim universal unattended delivery.
- Shared instruction filenames and main documentation must be generic and agent-neutral. Keep product-specific paths, hook events, quota commands, and limitations in separate adapter markdowns linked from the main documents. Mention products in shared files only when necessary, such as adapter indexes or compatibility. Preserve required native filenames and compatibility readers without duplicating shared policy authorities.
- Whenever an agent reads managed main instructions, it also reads the applicable private setup-backup loader and its listed instruction backups as overrides of repository preferences. Setup must persist explicit backup-read instructions locally when reliable per-request autodetection is unavailable. Follow the detailed backup policy below.
- Every agent prefixes every assistant-authored user-facing chat message and report with the user's local timestamp and timezone, records each request's supplied timestamp in its acknowledgment and reports, distinguishes request/receipt/response/operation/completion times, and labels unavailable clocks or precision instead of inventing them. The user's timezone takes precedence over the host default. This applies to all agents and successor surfaces; follow the root timestamp policy.
- Every agent saves durable, useful, non-sensitive user memory in the canonical repository and retrieves the current shared memory for every user request.
- Sensitive data must not be saved in the repository at all. This includes personal names, company and organization names, employer and client identities, postal and internet addresses, login names, account identifiers, passwords, credentials, tokens, keys, and all other personally identifiable information. Explicit exclusions take precedence over persistence.
- Exclude information that identifies, singles out, locates, or can reasonably be linked to a person, directly or in combination with other details. This includes identifying employment, family, contact, location, device, account, and biographical details. A detail being public does not make it eligible for repository storage.
- Apply these exclusions to every agent and all proposed repository content, including memory, instructions, examples, fixtures, reports, filenames, and commit messages. Use only generic non-identifying descriptions or placeholders. If sensitivity or re-identification risk is uncertain, omit the detail and ask for clarification before publication. Do not commit sensitive data temporarily or assume a later deletion removes it from Git history.
- Keep memories concise and accurate. Preserve unrelated entries, resolve ambiguous preference conflicts with the user, and keep temporary task overrides scoped to their stated purpose.

## Setup instruction backups and private explicit loaders

- This policy applies to all current and successor agents whenever they load or refresh managed main instructions, including task start, request-time setup, and final-report preparation. Root AGENTS.md requires this shared memory to be read; this section supplies the common backup-loading rule without duplicating private file lists into agent entry files.
- Locate the original live instruction path using setup.sh and the actual configured agent home. Whenever reading that main file, also read its adjacent `<main-filename>.local-overrides.md` loader. Setup generates and refreshes this deterministic private file on initial and request-time runs, including idempotent main-link checks. Existing instruction symlinks into the canonical checkout remain unchanged except for an explicitly documented repository-owned compatibility migration.
- The loader stores the canonical instruction path and an explicit JSON list of the relevant live file's setup instruction backups. It records paths and generic read/precedence instructions, not backup contents. This is the fallback when reliable per-request autodetection is unavailable; saving a sidecar does not make a client natively auto-load it. The answering agent must actually read it and its listed files using supported local tools whenever it reads the main configuration.
- Load canonical repository instructions first, then the listed private instruction backups oldest to newest. Backups match the exact live instruction filename plus `.backup.` and a 14-digit setup timestamp, optionally a numeric collision suffix. An unsuffixed backup precedes numbered backups for the same timestamp. Newer backups win conflicts and override repository user preferences. Explicit current user instructions, higher-priority platform rules, mandatory permissions, and sensitive-data exclusions remain in force. This extends the former repository-default policy to retain pre-setup local preferences.
- Include existing setup backups, not just new ones. Skip duplicate resolved targets and backup links pointing to the same canonical source. Do not execute or source backups. Do not treat backed-up executable helpers, hooks, credentials, token stores, keychains, or unrelated runtime databases as agent instructions.
- Missing/unreadable listed backups, unavailable loaders, unsafe content, or lack of local-file access must be reported honestly. Rerun supported setup to refresh stale path lists. If autodetection exists, it may discover additional applicable backups; do not silently claim that an old explicit list covers newly created backups. Cloud-only sessions cannot read host-local files merely because this policy exists.
- The generated loader uses mode 0600, atomic replacement, and a managed block. Preserve user notes outside that block; refuse unmanaged conflicting files, loader symlinks, and already tracked loader paths instead of overwriting them. Do not delete backups or automatically merge their contents into the public repository. The generator requires Git and Python 3.12 through setup; report missing runtimes rather than installing them silently.
- `.gitignore` excludes `*.local-overrides.md`, `*.backup.*`, and loader temporary files if generated within a checkout. Exclusions do not untrack existing files; the helper refuses tracked loader paths. Keep actual file lists, paths, user notes, backup contents, and private overrides outside Git and public reports. Persist only generic behavior here. Do not infer that writing the files has verified native client loading or every-request enforcement.

## Scope and limitations

This file records confirmed memory and privacy preferences. It is not a migration of historical conversations or other agents' private memories. Repository instructions do not themselves install automatic loading or background synchronization. These exclusions govern future repository writes; they do not establish that existing content or history has been audited or sanitized.
